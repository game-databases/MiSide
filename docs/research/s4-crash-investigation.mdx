## Root cause

1. **The poison is one self-referential serializable class** — [dump.cs:99328](../../extracted/il2cpp/dump.cs):
   `public class ConsoleEditor_HierarchyCase { … public List<ConsoleEditor_HierarchyCase> casesMe; }`.
   The dev-console component family (`ConsoleEditor`, TypeDefIndex 1429-1431) nests its own type.
2. **AssetStudioMod's converter has no cycle guard**: `AssetStudioUtility/TypeDefinitionConverter.cs`, custom-class branch emits a node then unconditionally constructs a child converter and recurses — `List<T>` → element `T` → field `List<T>` → … unbounded, ~3 frames per hop, blows the 1 MB thread stack. Crash-point variance across runs (790/1187/146 objects) is parallel-export ordering, not flakiness.
3. **Upstream has no fix to bump to**: v0.19.0 (2025-09-04) is the latest release of aelurum/AssetStudioMod, and that file is untouched since Perfare's 2022 (`git log` on path: last change 2022-11-17). This is why X-1's "tool version bump" remedy was a dead end.
4. **E1 correction (changes a recorded fact):** MiSide MonoBehaviours DO have stripped typetrees — UnityPy census: `level1` 0/82, `resources.assets` 0/979 embedded trees. E1's "Type trees NOT stripped" was wrong; all typing ever came from the `--assembly-folder` DummyDll route. Consequence: dropping assemblies (R1) silently degrades every dump; `--keep-going`, filters, mode flags, and arg order are all irrelevant to the overflow.

## Fix (built and proven on this run)

Cycle guard in `TypeDefinitionConverter` (local source clone `work\is4\src\`, upstream commit `6b66ec7`, csproj Version bumped 0.19.0.0 → **0.19.0.1**):

```csharp
private readonly HashSet<string> InProgressTypes;          // shared down the recursion
public List<TypeTreeNode> ConvertToTypeTreeNodes() {
    if (!InProgressTypes.Add(TypeDef.FullName ?? …)) {     // re-entry = cycle
        Logger.Warning($"Recursive serializable type \"{selfKey}\" detected; …");
        return nodes;                                      // node already emitted by caller
    }
    try { ConvertFields(nodes); } finally { InProgressTypes.Remove(selfKey); }
}
```

Build (natives staged from the stock release zip into `AssetStudioFBXNative|Texture2DDecoderNative/bin/x64/Release/`):
`dotnet build src/AssetStudioCLI -c Release -f net8.0 -p:TargetFrameworks=net8.0 -p:RuntimeIdentifier=win-x64 "-p:SolutionDir=<src>\\"`.

Evidence: R4 green on the exact poisoned probe; byte-parity multiset on `resources.assets`; 51/51 sweep; truncated node costs nothing observable (the one inspected `ConsoleEditor` instance has `casesRoot size = 0`; Unity itself caps inline serialization depth, so real assets are finite). Honest caveat for the residue ledger: inside affected objects the cyclic field's nested tail is not expanded — bounded loss confined to dev-console scaffolding fields.

**RECOMMENDED fix = (a)+(b) combined:**

- **(a) Corrected pin:** S4 runs the SAME pinned argv shape against AssetStudioModCLI **0.19.0.1** built from aelurum/AssetStudioMod `6b66ec7` + the cycle-guard patch above (source + binary live under `D:\unpacked_game_data\MiSide\work\is4\`; CodeWriter moves the patch into the repo tool tree and records versionSource "local rebuild, natives from stock 0.19.0.0 zip" in EXTRACTION-LOG.md).
- **Spec errata:** §2 S4 tool line gains "0.19.0.1 (local rebuild: recursive-type guard); stock 0.19.0.0 crashes with STATUS_STACK_OVERFLOW on self-referential MonoBehaviour types (ConsoleEditor_HierarchyCase)". AC-8 unchanged otherwise — output format is byte-identical where no cycle exists. §7 table: R-E1-1 resolved by measurement (sweep = 121 s total, budget no longer unknown). F3 (probe ignores `--keep-going`) remains open as an independent hardening item but is no longer load-bearing.
- **(b) Fallback design (only if the owner rejects a local fork):** per-container UnityPy typed dump requires a DummyDll→typetree generator with its own cycle detection — UnityPy's `TypeTreeGeneratorAPI` helper is not pip-installable (needs pythonnet + separate C# build), so this is strictly more work than the 20-line patch; not recommended.

## I-2 diagnosis (detect Unity-version empty string)

[pipeline/stages/detect.py:29-31](../../pipeline/stages/detect.py): `_read_unity_version` treats the first NUL-terminated run of `globalgamemanagers` as the version. Reality (byte-measured + UnityPy cross-check): the file is a SerializedFile **v22** whose head is binary header — leading 12 bytes are NUL, metadata_size 1668, data_offset 4096; ASCII `2021.3.35f1` begins at **offset 48** (length-prefixed). `raw.split(b"\x00")[0]` therefore returns `b""` for ANY such file → `""` warned, propagated into detect.json, stage report, and the EXTRACTION-LOG pin block.

Corrected read (stdlib-only, header-layout-proof):

```python
m = re.search(rb"\d{4}\.\d+\.\d+[fpb]\d+", raw[:256])
unity_version = m.group(0).decode("ascii") if m else ""
```

Spec errata: AC-6 wording "leading string of globalgamemanagers" → "Unity version string embedded in globalgamemanagers' SerializedFile header (offset 48 on buildId 19029065; never at offset 0)".
