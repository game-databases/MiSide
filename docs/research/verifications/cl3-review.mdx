### HIGH-2 — CL-1's anti-fake predicate cannot hold post-trigger: a correctly re-pinned corpus holds exactly ONE distinct build_id while changesets legitimately exist

Spec quote: CL-1 (l.504) "build FAILS if any changeset/renames artifact
exists while `fingerprints.json` holds <2 distinct `build_id`s"; §13-OQ-1
"the claim activates mechanically at build #2 via S9".

Evidence: `_meta.patch_day` (fingerprints.json, quoted verbatim in spec
§0.1): "a new buildId invalidates every fingerprint; rerun re-pins them"
— re-pin is **replacement**, not accumulation; measured today all 84 rows
carry the single value `19029065`, and nothing in the spec records the
prior pin anywhere. So on trigger day the committed corpus has ONE
distinct build_id plus valid changesets ⇒ the gate as written fails
every legitimate post-trigger build, pressuring implementers to weaken it
(exactly the path around the anti-fake law this AC exists to close) or to
pollute fingerprint semantics with stale rows. Worse, the *transient*
mid-rerun state (some rows re-pinned, some not) is the one moment
"<2 distinct ids" flips true — an accidental-arm window keyed to commit
timing, i.e. noise, not evidence of two trees.

The gate IS correctly placed at emit time (not render time) — keep that.
Fix the predicate to one of: (a) **structural authorship** — changesets/
`evidence_class:"computed"` rows may exist only when produced by M2 in
the same run that verified two trees (mirrors the spec's own §3.3
structural refusal, which is sound); or (b) **prior-pin record** — M2
writes `changelog/_pins/<from>.json` (or equivalent) before re-pin and
the gate requires that record per changeset `<from>`. Re-proof CL-1 both
pre-trigger (refusal) and post-trigger (acceptance) in the suite.
