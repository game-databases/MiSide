## Security-law audit

**Does the escape-first law actually bind? Yes.**

1. **Deny is structural, not advisory.** §2 states M2 validates on the SAME lexer
   AST it already walks for TOC/word counts and fails the build on ANY token of
   type `html` at ANY depth (block or inline), naming file + offending snippet;
   §5 repeats it as "enforced, not assumed" and kills the old false
   escape-by-default claim. There is no remaining sentence in the spec asserting
   HTML inertness without this mechanism. JSX needs no separate rule and the spec
   says why (no MDX runtime ⇒ tag-shaped text is inert text caught by the same deny).
2. **The javascript: hole is closed in the written law.** Link destinations are
   restricted to an ALLOWLIST (`http:` / `https:` / `mailto:` / relative /
   `#fragment`). An allowlist is fail-closed: any scheme not literally listed —
   including `javascript:` in any casing, whitespace/control-obfuscated forms,
   `data:`, `vbscript:`, entity-encoded variants (which either decode to a banned
   scheme or carry a colon that disqualifies them as "relative") — fails the walk
   with the same build-failure mode. The arbiter's named attack string
   `[x](javascript:…)` appears verbatim as a seeded C14 violation.
3. **C14 covers the required proof shape**: all four seeds each produce nonzero
   exit naming file+token; clean tree exits 0; emitted body HTML greps clean of
   raw-HTML signatures; C9's source grep demoted to belt-and-braces. Complete
   against arbiter F4.
4. **Residuals (LOW, recorded, none reopen the hole):**
   - The allowlist sentence says "link destinations"; image tokens (`![…]`)
     carry destinations too and §5 bans only REMOTE images. An implementation
     that walks only `link` tokens would leave image-src unvalidated. Practical
     exposure is negligible (img-src javascript: does not execute in modern
     browsers) and the html-token deny still blocks hand-written `<img>`, but
     M2 should validate BOTH token types — worth one clause at implementation.
   - C14's emitted-HTML grep includes `<img`, but markdown generation CAN
     produce `<img>` from local `![alt](src)` syntax — see Finding 1.

## Findings

All LOW; none reopen the security law or break a design law. Recommend carrying
them to the board rather than reopening the fix round:

1. **C14 grep-list nit** — `<img` is listed among "raw-HTML signatures markdown
   generation cannot produce", but local `![alt](src)` image syntax produces
   `<img>` legitimately; §5 bans remote images only. As written, a guide with a
   local screenshot fails C14's secondary grep spuriously (fail-closed
   direction). Fix at implementation: either ban inline body images outright or
   drop `<img` from the signature list (keep `<script`, `<iframe`, `onerror=`);
   the enforcement of record (token deny + allowlist + seeded exits) is
   unaffected. Inherited verbatim from arbiter F4 wording, faithfully transcribed.
2. **Cartridge phrasing** — "23/23 cartridge rows ship `name_loc: null`": disk
   truth is the key is ABSENT in all 23 rows (0 substring hits), not null. The
   shorthand originates in missingdata.md CAR-5 itself. Behavior is fully pinned
   anyway because V3 rule 3 handles absent AND contentless cells; suggest
   "carry no name cell at all" next time the line is touched.
3. **MT-non-goal citation gloss** — the spec's "(for missing GAME locales)"
   adds an interpretive word to localization-architecture.md:82's literal
   "missing locales". The operative gate is intact regardless (§8.2 + §12: no MT
   tooling without an explicit register entry), so this weakens nothing; noted
   for citation honesty.
4. **`link_terms[]` attachment grammar unpinned** — the frontmatter example's
   plain-string `entities[]` entries cannot carry a per-entity `link_terms`
   field; M1's validator schema must pin the form (structured entries or a
   keyed map) before authoring starts. Mechanical, no design rework.
