### M-3 renderer security law — ACCEPT, binding the escape-first pipeline

Reviewer is right on both counts: stock `marked` passes raw block/inline
HTML through by default, its `sanitize` option was removed in v5+, and C9's
grep cannot catch arbitrary injected HTML (`<img onerror=…>` passes every
listed pattern). Since `site/package.json` pins no markdown dep today, M2
gets exactly what the spec says — so the spec must state the law the
toolchain will actually hold. Ruled law (escape-first, no sanitizer dep):

- **M2 validates before rendering, on the lexer AST it already walks** for
  TOC/word-counts: any token of type `html` at ANY depth (block or inline)
  fails the build, naming file + offending snippet. No raw HTML ever
  enters an article body; consequently `marked.parse()` output contains
  only markup generated from markdown syntax itself.
- **Href protocol allowlist in the same walk**: link destinations are
  restricted to `http:`/`https:`/`mailto:`/relative/`#…`. This closes the
  `[x](javascript:…)` hole the reviewer did not name — same validator,
  same failure mode.
- JSX needs no separate rule: without an MDX runtime, JSX in `.mdx` is
  inert text, and any tag-shaped text is caught by the html-token deny.
- §5's claim is rewritten from the false property ("escape-by-default
  rendering keeps HTML inert") to the enforced mechanism above.
- **New enforcing AC (C14)** with seeded-violation proof — see F4. C9's
  source-grep extension stays as belt-and-braces but is no longer the
  enforcement of record.

No sanitize-class dependency is added; one pinned dep (`marked`) survives,
which also keeps the L-2 amendment minimal.

### M-4 V3 deterministic linking — ACCEPT, tie-break semantics ruled

All three edges confirmed on disk (shared Menu-83 pointer ×2;
23/23 cartridge rows `name_loc:null`; per-locale holes precedented by
MA-2/CAR-9). V3 becomes mechanical only after these rules land in §4:

1. **Shared display names never auto-link.** If two entities listed in one
   article resolve to byte-identical display strings in a locale, NONE of
   the colliding names links in that locale. First-listed-wins was
   rejected: it silently attaches the wrong entity's link, which is worse
   than no link. Reverse-link modules and `entity-cards` embeds are
   unaffected — the collision suppresses body-text linking only. Authors
   who need the link use frontmatter `link_terms[]` (below) to pin an
   unambiguous string.
2. **Nameless rows link zero occurrences by default**, matching CAR-5's
   measured-absence posture. Escape hatch stays inside the declared-set
   principle: optional per-entity frontmatter field
   `link_terms: ["Exact String"]` — exact case-insensitive whole-token
   match, first occurrence per term, reviewable in diff like everything
   else V3 does. Community aliases are NOT auto-scavenged (fuzzy matching
   stays banned); they may be declared explicitly via `link_terms`.
3. **Per-locale resolution, omit on empty.** Names resolve through THAT
   locale's loc pointers; an absent/contentless name cell yields no link
   in that locale — never an EN-string fallback (omit-never-mix, §8.1).
   The "identical across locales by construction" guarantee is honestly
   weakened to: link positions are identical wherever names resolve;
   locales with hole-y names omit those links.

## OQ-1 owner briefing — assessment & recommendation

**Are A/B/C costed fairly?** Substantively yes after the L-3 wording fix,
with two corrections the briefing should carry:

- Option B's cost is understated: reusing client-shipped terminology via
  `resolveLoc` pointers requires emit-side term-resolution support in M2 —
  real tooling B has and A doesn't. Fair cell: slowest-to-moderate pace,
  highest fidelity where readers notice (game terms), moderate new
  tooling, highest editorial overhead per article.
- Option C's true bottleneck is reviewer capacity, not generation: finding
  named human reviewers for all 34 (incl. ar-EG, pl, tr…) is the schedule
  term; MT drafting is nearly free. Also carries the register-entry
  override requirement against localization-architecture line 82, whose
  non-goal is scoped to missing GAME locales — so the override is a
  legitimate ask, not a rule-break.

**Should per-locale tiering become option D?** Yes, but labeled honestly:
tiering is wave-shaping, not translation authority — it composes with any
of A/B/C. Presented as a fourth row it gives the owner a concrete "start
now" choice instead of an all-or-nothing matrix:

> **D. Staged rollout (wave-shaping hybrid)** — chrome+UI stay fully
> localized ×34 immediately (already shipped and parity-enforced — this
> plane is unconditional and NOT gated by OQ-1). Long-form articles launch
> pivot EN + RU (RU human-authored: co-primary audience per scout §3.3,
> small volume, community-translatable); remaining locales follow behind
> whichever authority wins. Cost: near-term cheapest honest path, zero MT
> pressure at launch; consequence: non-RU non-EN guides arrive late
> (omit-fallback keeps honesty throughout).

**Recommendation to the owner:** D as the rollout frame + B's terminology
reuse where pointer plumbing exists; escalate to C only via an explicit
register entry quoting the Note#7 text and naming per-locale reviewers;
A remains available if the owner wants zero tooling. Whatever is chosen,
the register entry quotes the tasking-prompt note (M-2) and states the RU
first-wave commitment (L-3). The pipeline builds identically under all
four — nothing downstream blocks on this except mass non-pivot authoring,
which stays frozen until the ruling.
