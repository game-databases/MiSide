**Decompile-depth caveat (same classes as DS-2).** `decompiled/main/**` is
ilspycmd-over-DummyDll output: signatures, field offsets and tokens are real;
**method bodies are empty**. Every claim below is classed:

- **[proven-hard]** — serialized in a dump we hold; byte-level evidence reproducible.
- **[proven-structure]** — class/field/token pinned in `decompiled/` or `dump.cs`.
- **[unverified-behavior]** — needs IL2CPP native bodies or a scene parse we do not hold yet.
- **[community]** — wiki/guide context, labeled, never evidence.
- **[negative-finding]** — a thing measurably ABSENT from the corpus (recorded because
  Principle zero forbids silent drops in either direction).

## 1. Scope

### 1.1 Owned rows

1. **`profile_document`** — the SPEC entity kind (~12 `[unverified]`). This spec replaces
   that estimate with a measured candidate set: **14 rows keyed 1:1 onto the character
   registry's Mita entries** (§3), of which 11 have a placed pickup in the client, 2 are

   `note` (**160 instances across the 23 level scenes**, §2.1),
   `paper_part` (5, §2.5), `novella_surface` (1, §2.4), `book` (8 titles ×34 locales, §2.3).

## 2. Corpus reality (all measured 2026-08-25)

### 2.1 Notes — `Unity_Note` (family `note`)

- Class truth: [`Unity_Note.cs`](../../extracted/decompiled/main/Assembly-CSharp/Unity_Note.cs)
  `[AddComponentMenu("Functions/Unity/Note")]`, Token `0x2000077`, **zero serialized
  fields** beyond the MonoBehaviour base. Every one of its dumps confirms it:
  `m_Name = ""` and nothing else
  (e.g. [level5/Unity_Note_#20261.txt](../../extracted/harvest/mb-dump/level5/Unity_Note_#20261.txt)).
  **[proven-hard]** — the component itself carries no payload.
- Census: **258 instances** across the dumped containers, of which **160 sit in the
  23 level scenes** (level0 has none): level5 17 · level14 13 · level8 12 · level16 10 ·
  level12 9 · level4/6/7 8 each · level22 7 · level9/10 6 each · level13/17 6 each ·
  level2/15/20 5 each · level3/11 5 each · level18/19/21/23 4 each · level1 3. The other
  98 are the same shared prefabs re-listed under `sharedassets*/globalgamemanagers/
  resources` by AssetStudioMod dependency auto-load (E1 deviation 6) — dedupe rule in §7-R4.
  Filename-census method: `ls mb-dump/<container>/Unity_Note*.txt` (bare file = first,
  unsuffixed instance); the non-level copies live in the shared-asset containers of the
  51-container dump set, never in a level file. **[proven-hard]**
- What a note GameObject carries (sampled exhaustively at level5, GO pathIDs
  43–403/1615/1854/1855/2534/2883): `Image` (sprite PPtr), `Button`,
  `Events_Data`/`Time_Events` persistent calls into `ObjectDoor.Lock`,
  `ObjectDoor.LockSharply`, `World.HintLocationHide`, `ObjectInteractive.Activation`,
  `Transform_Position.ResetParent`, `GameObject_Destroy`, plus `Light_Glass` on one.
  Notes are **interactive trigger props with serialized event wiring** — the wiring is
  joinable today (§5-J5); the *displayed* content is not serialized on the component
  (§7-R1). **[proven-hard]** for the wiring; **[unverified-behavior]** for rendering.
- Content carriers considered and their evidence: loc layer — ruled out (§1.3-2);
  scene `Text` children — ruled out (§1.3-3); baked paper textures — plausible but
  **unresolved**: the two distinct sprite pointers observed on level5 note Images
  (pathID 49 ×2, 919 ×2, 0 ×1) cannot be named yet because no container-scoped
  sprite-pathID→export-name index exists on disk (§7-R5).

### 2.2 Profile documents — where the client actually keeps them

The wiki models *cartridges* and *Mita Profiles* as two families
([D1 §3](../research/game-research.mdx) items 1 and 3). Client evidence unifies them:

1. **One pickup family.** All placed pickups are `FlashTaker` instances whose single
   payload field is `string save`
   ([FlashTaker.cs](../../extracted/decompiled/main/Assembly-CSharp/FlashTaker.cs), offset 0x18).
   Corpus census: **21 placed pickups**; keys split exactly into 11 `mta*`/`mla`
   (Mita-side) + 10 `plr*` (player-side) — full table in §3. Collection literal
   `/Save/Flashes` ([stringliteral.json](../../extracted/il2cpp/stringliteral.json)). **[proven-hard]**
2. **One text family.** The gallery registry binds each Mita row to its lore paragraph
   by index: `MenuPersonage.resourceMita[i].indexDescriptionStringFile` →
   `Personages.jsonl` lines 1–14 ([DS-1](dataset-characters.mdx) §3, S1/S6). Those
   paragraphs ARE the profile prose the wiki tabulates. **[proven-hard]** for the pointer;
   **[community]** for the textual identity with the wiki's Profiles page (diff pending, §7-R2).
3. **One achievement pair over the two key prefixes.**
   [DataAchievements.txt](../../extracted/harvest/mb-dump/resources.assets/DataAchievements.txt):
   `lineTranslate = 12` ↔ `ACHI_cartridgeplayers`, `lineTranslate = 13` ↔ `ACHI_mitastory`;
   `Achievements.jsonl#line_index=12` = "Caught Them All" (all `plr*`),
   `#line_index=13` = "Hi, Mita" (all Mita-side). Same split already encoded in
   [contracts/dataset-achievements.mdx](../../contracts/dataset-achievements.mdx)
   (`collectible_set`: `player-cartridges` id 12, `mita-profiles` id 13). **[proven-hard]**
   for the pairing; **[unverified-behavior]** for the counting predicate (code body empty).

**Adjudication rule (pinned).** `profile_document` rows are emitted **keyed to the 14
Mita registry entries** (subject + lore text + pickup placement), NOT as free-standing
papers. Falsifier: if the P5 scene parse or a future native decompile surfaces a second
serialized profile registry (a profile screen object, a second save-key family), the
emit pass forks `profile_document` away from cartridge identity and ledger both shapes —
never silently merge.

## 4. Schema

### 4.1 Locale ruling — inherited unchanged from DS-1 §4.1

Loc **pointers**, never per-locale copies: `{category, line_index}` objects resolved at
render time through the proven `GlobalLanguage.GetString` authority (E1 step 7).

[contracts/dataset-endings.mdx](../../contracts/dataset-endings.mdx): loc rows are cited
only as `<file>.jsonl#line_index=<n>`.

## 6. Stub-first plan

Same ladder as [DS-1 §6](dataset-characters.mdx#6-stub-first-plan-promptfordb-hooks):

1. `registered` — profile rows 0–13 above: full record, nothing stubbed.
2. `loc_only` — n/a today (every Personages line 1–14 is consumed by a registry row;
   if a future registry bump leaves an orphan line, it lands here with
   `status: "loc_only"` and empty identity fields).
3. `unregistered candidate` — note/novella instances are ALL registered by census
   (nothing is dropped), but any GameObject a future P5 parse shows to be a *label*
   rather than a paper (e.g. dev leftovers like the `Speed = 0.1` Text) demotes to
   `world_documents.jsonl` rows with `status: "candidate"` + locator, never deleted.
4. Wiki-only claims (per-note transcriptions, profile locations that disagree with the
   FlashTaker census) — **no row, no field**; they may appear only as
   `evidence_class: "community"` context in the README, never in data rows
   (SPEC non-goals: no fan-lore authoring in data rows).

Every non-`registered` row carries `missing_fields: [...]` for mechanical
missingdata.md generation.
